# CosyVoice Reader — 疑难问题修复记录

本文件记录 2026-10-18/20 这几轮排查中，**真正难查、容易被误判**的四个故障。
每个都附了根因、证据和修法，方便以后重现时直接对上号。

## 一、电子书一直失败：wetext 的「空字符串」陷阱

### 症状
导入 `.epub` / `.mobi` / `.azw3` 后，任务一开始就失败，报错信息非常含糊：

```
AssertionError
```

或者更隐蔽的一种——**不报错，但任务卡在 0 段再也不动**。

日志里对应的是：

```
File "CosyVoice/cosyvoice/cli/frontend.py", line 161, in text_normalize
    if text[-1] not in pounc:
IndexError: string index out of range
```

### 根因
CosyVoice 内置的文本正则化库 `wetext` 对**中英混排、带 URL、带符号的文本**会出问题：

- `wetext/token_parser.py:68` 有 `assert len(input) > 0`
- 上游 `wetext/utils.py` 的 `normalize()` 流程是
  `preprocess → should_normalize → tag → reorder → verbalize`
- 当 `tag()` 对某段文字返回**空字符串**时，`parse('')` 直接触发断言失败
- 更糟的是有时它**不抛异常，而是静默返回空串**，于是下游 `text[-1]` 越界，
  或者拿到空文本去推理，任务就无声无息地停住了

### 触发条件（实测矩阵）
把整本书逐段喂进 `wetext` 做二分，定位到这几类片段会炸：

| 触发片段 | 说明 |
|---|---|
| `#` 紧跟数字或 `#` | 如 Gutenberg 版权页的 `[eBook #1342]` |
| 符号与数字相邻 | `# * \| / ~ ^ _ + = & % @ $ [ ]` 等 |
| URL 片段 | 如 `.../www.gutenberg.org/license.` |

### 修法（两层保险）
**第一层——文本侧消毒**（`document.py`）：

- `_WETEXT_TRAP`：把 `#` 后跟数字/`#` 的情况拆开
- `_WETEXT_SYM = r'#*|/~^_+=&%@$\[\]'`：符号与数字相邻时插空格
- 对外两个函数：`tts_safe(text)`（常规消毒）和 `tts_safe_hard(text)`（更激进，用于兜底重试）
- `load_text()` 出口统一走 `tts_safe`

> 踩坑记录：一开始把 `{ } < > \`` 也放进 `_WETEXT_SYM`，结果把 `{{` 拆成了 `{ {`，
> 反而制造了新的失败。这几个字符**不要**加进去。

**第二层——调用侧兜底**（`backends/cosyvoice3.py` 的 `install_frontend_guards()`）：

不修改 vendored 的 `CosyVoice/` 源码（那是上游仓库），而是在 `CosyVoice3Backend.__init__`
里给 `zh_tn_model.normalize` / `en_tn_model.normalize` 打补丁：

- 抛异常 → 回退到原文
- 返回空串 → 回退到原文

同时把 `_safe_split_paragraph` 同时装进 `cosyvoice.utils.frontend_utils` 和
`cosyvoice.cli.frontend` 两处（后者是 `from ... import` 进来的引用，必须一起换）。

**第三层——段落级重试**（`backends/synthesize.py`）：
单段合成失败时，用 `tts_safe_hard` 再过一遍重试，避免整本书因为一段怪字符全废。

### 回归测试
- `scripts/test_ebook_import.py` — 42 项
- `scripts/test_frontend_guard.py` — 11 项
- 用真实样本（Gutenberg 的 `test.epub` / `test_mobi7.mobi` / `test_kf8.azw3`）逐段扫描：
  epub 0 抛异常 0 空串、mobi 0 抛异常 1 空串、pdf 0 抛异常 0 空串

## 二、文件名里那个看不见的空格：WinError 3

### 症状
《弑君者传奇》这本 azw3 每次都是 0/457，秒失败：

```
FileNotFoundError: [WinError 3] 系统找不到指定的路径。:
'F:\hanaco\project\cosyvoice_reader\outputs\resumetest\弑君者传奇：风之名 ([美] 帕特里克·罗斯福斯  \segments'
```

注意路径里 `罗斯福斯` 后面那**两个空格**。

### 根因
用户的书名是 `弑君者传奇：风之名 ([美] 帕特里克·罗斯福斯  .azw3`
（标题和扩展名之间有多余空格）。

- `Path('...罗斯福斯  .azw3').stem` → `'弑君者传奇：风之名 ([美] 帕特里克·罗斯福斯  '`（**尾随空格保留**）
- 以它建目录后，Windows 会**静默吃掉目录名的尾随空格**，但 `mkdir` 内部拿未修剪的名字去核对，于是报「找不到路径」
- Linux 上完全不会有这个问题——这是纯 Windows 坑

### 修法
`config.py` 新增两个统一入口：

- `safe_text(text, fallback='document', max_len=MAX_STEM_LEN)` — 去非法字符 `<>:"/\|?*`、
  去掉尾随空格和点、避开 Windows 保留名（CON/PRN/AUX/NUL/COM1…）、超长截断
- `safe_stem(filename, fallback='document', max_len=80)` — 取 stem 后走 `safe_text`

三个调用点全部改用它：

- `app.py` 的 `_safe_upload_name`
- `ebook_import.py` 的 `free_text_path`（提取出的 .txt 路径）
- `backends/synthesize.py` 的 `probe_resume()` 与 `synthesize_core()`（工作目录名）

顺带修的：源文件不见了（临时上传目录被定期清理）时，原来报的是原始异常，
现在给友好提示「源文件已不在了（临时上传目录会定期清理）。请把这本书重新拖进来再试。」

### 回归测试
`scripts/test_safe_names.py` — 30 项，标记 `SAFE_NAMES_OK`。

## 三、任务「假死」：stdout 被接进了没人读的管道

### 症状
任务正常启动、GPU 也跑了一阵，然后**整本书一动不动**：

- GPU 利用率掉到 0%
- CPU 也不烧
- 显存还占着 11 GB
- **日志一个字都不再增长**
- Web UI 上进度条卡住

重启后一切正常——所以特别容易被当成「偶发」。

### 根因（用 py-spy 抓线程栈定位）
```
Thread-7707  emit (logging\__init__.py:1113)      ← 想写日志，拿不到锁
Thread-7708  acquire (logging\__init__.py:927)    ← 持有写句柄，卡在 write
   ↑ 两者都在 cosyvoice.py:101 inference_zero_shot → logging.info
```

链路是这样的：

1. `start.bat` 启动 python 时，**stdout 继承自一个已经被关掉/没人读的 cmd 管道**
2. 管道缓冲区写满之后，`write()` 就**永久阻塞**
3. 而这次写发生在 `logging` 的 handler 里，**写的时候握着 handler 锁**
4. 于是所有想写日志的线程全部排队等待，一起死锁

因为日志写不出去，所以**表面上什么都看不到**，这是最坑的地方。

### 修法（两层）
**第一层——启动脚本重定向**（`scripts/start.bat`）：

```bat
if not exist "logs" mkdir "logs"
".venv\Scripts\python.exe" -u app.py >> "logs\reader.log" 2>&1
```

只要 stdout 落在**真实文件**上，就永远不会阻塞。

**第二层——进程内兜底**（`app.py` 的 `_setup_output()`，在 `__main__` 最前面调用）：

- 自动建 `logs/` 目录
- `reader.log` 超过 8 MB 就截断（Windows 上 cmd 的重定向会占着文件柄，
  所以这步包了 try/except，失败不影响启动）
- **如果 stderr 不是真实文件**（说明没走 start.bat，或者又接到了管道上），
  就自己打开 `logs/reader.log` 并接管 `sys.stdout` / `sys.stderr`
- 把已有的、指向旧流的 `StreamHandler` 用 `h.setStream(target)` 重定向过去
- 装一个 `logging.FileHandler`，再用 `_UiLogHandler`（WARNING 以上转发到 UI 日志面板）
  保证「UI 里能看到的」和「文件里能查到的」是同一份

### 怎么快速判断又遇到了这个问题
```powershell
# 任务不动时，直接看线程栈
.\.venv\Scripts\py-spy.exe dump --pid <python_pid>
```
如果栈里出现 `logging\__init__.py` 的 `acquire`/`emit`，就是它。
正常情况应该停在 `torch` / `cosyvoice` 的推理调用里。

## 四、新注册的音色整篇转不出来：参考音频超过 30 秒

### 症状
「声音资产库」里新建音色时**看着成功**（档案出现在列表里，能试听），
但用它转任何文档，任务立刻失败，错误列只有一句英文：

```
do not support extract speech token for audio longer than 30s
```

2026-10-20 的实例：`暮色.txt` + 音色 `喻大华`，22:25 和 22:28 两次都是这样，
另一个音色 `anna` 的同名文档却早就转完了——所以第一反应容易怀疑是某个文档有问题。

### 根因
CosyVoice 的 zero-shot 只接受 **≤ 30 秒**的参考音频，超过就直接断言：

```python
# CosyVoice/cosyvoice/cli/frontend.py:101
assert speech.shape[1] / 16000 <= 30
```

用户上传的 `prompt.wav` 是 **172 秒**的整段评书，`prompt.txt` 是 546 字全文（3.17 字/秒，
语速正常，文字稿并没有「多出来」）。于是：

1. `_profile_create` 写盘成功 → `register_all` → `register_spk` → `add_zero_shot_spk`
   → `frontend_zero_shot` 触发断言
2. `pool.register_all()` 把异常**吞进 `pool.last_error` 后返回 False**，
   旧代码没有检查返回值，所以 UI 收到的是「创建成功」
3. 之后每个任务在 `backends/synthesize.py` 的 `inst.register_spk(...)` 处再炸一次，
   整篇 0 段、直接失败——**档案建好了，但永远转不出来**

> 排查提示：这类「建得成、转不了」的问题，先看 `voice_profiles/<名字>/prompt.wav`
> 的时长。超过 30 秒就是本节。

### 修法
**一、建档案时就裁到 30 秒内**（`voice_profiles.py` + `audio.py`）：

- `audio.find_pause_cut()`：按 20 ms 窗 / 10 ms 跳算 RMS，阈值跟着录音自身底噪走
  （`min(p5+10, p90-18)` dB），在 `[18, 29.4]` 秒区间里找**离目标最近的停顿中点**切；
  整段没有停顿时退回 29.4 秒硬切，保证一定有结果
- `audio.trim_wav()`：先写 `*.part.wav` 再 `os.replace`，中途失败不会毁掉原文件
- 裁完的音频只有 27~29 秒，**文字稿必须跟着变短**，否则 zero-shot 的对齐会乱。
  这里用 whisper 听写只当「定位器」：

  ```
  find_pause_cut → trim_wav → transcribe(裁后的 wav)
      → _align_prefix(原稿, 听写) → 原稿按位置切前缀 → prompt.txt
  ```

  原稿完整留一份 `prompt.source.txt`，随时能回查修改。实测：
  - 172 秒 → 27.47 秒，对齐到前 70 字
  - 48 秒 → 28.05 秒，对齐到前 94 字（对齐覆盖率 1.00）

**二、注册失败必须回滚**（`app.py` 的 `_profile_create`）：
`register_all` 返回 False 就抛错，except 分支 `remove_all` + `delete_profile`，
**不留下一个永远转不出来的音色**，用户改完能原地重试。

**三、后端的最后一道闸**（`backends/cosyvoice3.py` 的 `register_spk`）：
时长检查放在 `with self.lock` 之前，报中文：

```
音色 [x] 的参考音频 172 秒，超过 CosyVoice 的 30 秒上限。请在「声音资产库」
删掉这个音色后重新新建（现在会自动裁到 30 秒内），或者换一段 30 秒以内的录音。
```

**四、UI 提前说清楚**（`index.html`）：
选文件后先读 `audio` 元数据拿时长，超 30 秒立刻提示「正在按停顿裁剪并对齐文字稿」，
成功后 toast 出裁剪结果；参考音频提示文案也改成了「建议 5~20 秒，最长 30 秒」。

### 为什么听写默认用 base 而不是 medium
同一段前 30 秒：`base` 4.4 秒、`medium` 43.9 秒。错字都不少（`奕纬` → `一为` / `易伟`），
但 difflib 对齐（按顺序吃匹配块，允许跳 24 字）**两者给出同一个切点 87 字**，
覆盖率 1.06 / 1.04。定位切点只需要「大致内容对得上」，所以默认 `base`；
需要更好听写时设环境变量 `COSYVOICE_PROMPT_ASR_MODEL=medium`。

> 踩坑记录：`find_pause_cut` 里停顿中点一开始写成
> `(starts[i] + (j-i+1)*hop)/2/sr`，等于把「结束位置」当成了中点，
> 结果切点落在一个字中间（回归测试里「切点附近是静音」这项直接抓到了）。
> 正确写法是 `starts[i]/sr + dur/2.0`。

### 已经建坏的老档案怎么办
老档案不会自己变好，用维护脚本原地重建（默认只预演，`--apply` 才动手）：

```powershell
.\.venv\Scripts\python.exe scripts\fix_long_voice_profiles.py          # 看看有几个
.\.venv\Scripts\python.exe scripts\fix_long_voice_profiles.py --apply  # 重建
```

脚本会优先拿 `prompt.source.txt`（没有则 `prompt.txt`）当原稿，
把旧目录改名 `<名字>.bak` 再重建，失败自动改回来。跑完**必须重启服务**，
让模型按新档案重新注册。

### 回归测试
`scripts/test_voice_profile.py` — 7 组 25 项，标记 `VOICE_PROFILE_OK`：

1. `find_pause_cut`：切在停顿上（切点 ±80 ms 内 RMS < 0.05）、不超 30 秒、不早于 18 秒、没停顿时硬切
2. `trim_wav`：返回时长与落盘一致、仍是 16k 单声道
3. `_align_prefix`：真实听写错字样本也能定位、覆盖率合理、完全跑偏时返回 0
4. `create_profile`：超长参考音频能建成、已裁到 30 秒内、meta 有裁剪信息、原稿另存、文字稿被裁短

6. 正常长度：12 秒照常通过、比例正常不打扰、过短被拒且不留目录
7. `register_spk`：超长音频抛中文错误（带音色名和秒数），不是英文断言
