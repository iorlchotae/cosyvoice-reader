# 篇内按段并发（每段一实例）设计

日期：2026-10-19
状态：已实现，测试全绿；**待切换**（等《山音》跑完再重启服务生效）

## 1. 需求与实测

用户反馈（原话）：「GPU，显存，内存都没用足，多上线程，提升效率」

实测（任务 `2db23b3c384e` 跑到 6.7 小时时）：

| 指标 | 实测值 | 说明 |
| --- | --- | --- |
| GPU 利用率 | 平均 59.5%（最低 41%，最高 95%，40 次采样里 31 次 < 60%） | 没跑满 |
| GPU 功耗 | 62 W / 上限 180 W | 明显在等，不是在算 |
| 温度 | 51 °C | 远未降频 |
| 显存 | 11482 / 16311 MiB（空闲 4829） | 一个实例约 5.7 GB，塞不下第三个 |
| CPU | 48%（12 逻辑核） | 不是瓶颈 |
| 内存 | 15.7 / 31.7 GB | 模型在显存里，内存不是瓶颈 |

结论：**不是线程不够，是并行单位选错了。**

原来「并行」的单位是**文档**：一篇文档独占一个实例，段与段严格串行。
所以只有 2 本书时，2 个 worker 已经是上限——再调大也没有第三篇可跑。
更浪费的是：《山音》跑完后只剩《弑君者传奇》，第二个实例会**整天空转**
（约 18 小时），而单实例的吞吐只有双实例的约 70%。

## 2. 设计

新增「篇内按段并发」：**多个实例各领一段，提交线程按段序接表。**

- `synthesize_core(..., extra_backends=[...])`：非空且剩余段 > 1 时启用并发路径。
- worker 线程只做「合成 + 原子落盘 + 写 `NNNN.done`」，只碰自己那一段的文件，
  所以多线程互不干扰。
- **只有提交线程**改 `all_wavs / slice_wavs / acc / done_count`，并且严格从第 1 段
  往后退，因此：
  - 段序与串行完全一致（并发不会把顺序打乱）；
  - 10 分钟切片边界与串行完全一致（不变量 B 仍然成立）；
  - `NNNN.done` 仍是「这段已完成」的唯一判据（不变量 A 仍然成立）。
- 调度侧 `_dispatch`：只允许**最后一篇**吃多个实例。
  `pending == 1 and inflight == 0 and target > 1` 时把空闲实例都给它；
  两本书同时在跑时仍是一篇一个实例（篇间并发优先）。
- 只剩一篇时**必须先等实例加载完再开跑**：带着 1 个实例跑起来就再也改不了，
  会一路串到底。

## 3. 为什么不是别的方案

- **加到 3 个实例**：显存不够（空闲 4829 MiB < 单实例 5.7 GB）。而且只有 2 本书时，
  第 3 个实例本来也没东西可跑。
- **TensorRT**：已经在 2026-08-23 实测过，`RTF(TRT)=0.870` 对 `fp32 onnx 基线 0.871`
  ——**零收益**，还带 `DiT tensorRT fp16 engine have some performance issue` 的警告。
  不走回头路。
- **加大 `CHUNK_CHARS`**：flow-matching 的 DiT 对帧数近似二次增长，长段反而更慢，
  且会抬高单次显存峰值。

## 4. 改动清单

- `backends/synthesize.py`
  - `synthesize_core(..., extra_backends=None)`；
  - 循环拆成 `render()`（可并发）/ `finish()`、`carry()`（只在提交线程）；
  - 音色注册改成对**每个实例**都注册（音色表不共享）。
- `app.py`
  - `_dispatch`：最后一篇分到多个令牌；加载未完成时等加载；
  - `_run_doc(task, doc, tokens)`：接收令牌列表，`finally` 里逐个归还。
- `index.html`：`并行文档数` → `并行实例数`，提示语改成「只剩一篇时这篇按段并发」。
- `scripts/test_unit_parallel.py`：新增确定性测试（不加载模型）。

## 5. 验证

`scripts/test_unit_parallel.py` → `UNIT_PARALLEL_OK`

- 峰值并发 = 2，两个实例都用上（A=4 B=4）；
- 合并段序严格 `0001,0002,…,0008`；
- 并发下停止 → 半成品是**连续前缀**（4 段）且生成快照；
- 并发下续传 → 只补剩下的 6 段，最终 10 段顺序正确；
- 并发下 12 段 / 每 3 秒切片 → 仍是 4 块。

回归：`scripts/test_resume.py` → `RESUMETEST_OK`（串行路径未被改坏）。

## 6. 切换步骤（等《山音》跑完）

1. 确认《山音》`status=done`；
2. 重启服务（`scripts/start.bat`），旧任务的卡片会消失，但磁盘上的
   `resume.json` 与 `segments/*.done` 都在；
3. 只提交《弑君者传奇》这一篇（**不要**同时提交《山音》，否则又变成两篇分实例）；
   断点指纹匹配 → 从已完成的段继续；
4. 因为它是唯一一篇，调度器会等两个实例加载完再开跑，然后**按段并发**。
